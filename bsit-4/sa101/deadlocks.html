Definition

Everyone waits. Nobody can finish.

04
NORMAL LIFECYCLE

Request → use → release

A process asks for a resource before using it, then releases it when finished.

DEADLOCK

A closed waiting set

Every process waits for a resource that only another process in the same set can release.

The waiting set has no external escape.04 / 20
Necessary conditions

Deadlock needs all four ingredients.

05
🔒

Mutual exclusion

At least one resource cannot be shared.

✋

Hold and wait

A process holds one resource while waiting for another.

🧲

No preemption

Only the holder can release its resource.

🔁

Circular wait

Each process waits for the next process in a cycle.

Break any one condition and deadlock cannot form.05 / 20

Prevention

Break one link in the chain.

09

Share where possible

Read-only files need no mutual exclusion. Printers still do.

Remove hold and wait

Allocate everything before execution, or request only while holding nothing.

Allow preemption

If a process cannot get everything, make it release what it already holds.

Order resource types

Require requests in increasing resource order to prevent circular wait.

Prevention is simple, but can reduce utilization.09 / 20
Avoidance

Safe now means finishable later.

10

A state is safe when some process order lets every process obtain its remaining resources and finish.

An unsafe state is not necessarily deadlocked. It simply has no guaranteed completion sequence.

Safe

guaranteed route out

Avoidance keeps every granted allocation inside the safe region.10 / 20

Banker’s algorithm

The OS loans resources cautiously.

13

Each process declares its maximum demand. Before granting a request, the OS simulates the result and asks:

“Can everyone still finish?”

Core data

Available[M] free instances by resource type

Max[N][M] declared maximum demand

Allocation[N][M] resources held now

Need[N][M] resources still needed

Need = Max − Allocation
N processes • M resource types13 / 20
Safety algorithm

Search for a completion order.

14

Copy what is free

Work = Available; mark every process unfinished.

Find a process that can finish

Choose unfinished Pᵢ where Need[i] ≤ Work.

Simulate completion

Add its allocation back to Work and mark it finished.

Check the result

If every process finishes, the state is safe. Otherwise it is unsafe.

The algorithm tests possibility, not the actual runtime order.14 / 20

Handling a request

Grant it only after a safe rehearsal.

16

Validate

The request cannot exceed the process’s remaining need.

Wait if unavailable

The request cannot exceed currently available resources.

Pretend to allocate

Update Available, Allocation, and Need temporarily.

Run the safety test

Commit a safe result. Restore and wait if the result is unsafe.

Request₁ = (1, 0, 2) → safe
Request₄ = (3, 3, 0) → unavailable
Request₀ = (0, 2, 0) → unsafe
Availability alone does not make a request safe.16 / 20
Detection

If prevention is absent, look for cycles.

17

Single instance per resource

Remove resource nodes to create a wait-for graph. An edge Pᵢ → Pⱼ means Pᵢ waits for something held by Pⱼ.

A cycle means deadlock.

Multiple instances

Use a Banker-like search, but compare each outstanding Request with Work instead of comparing Need.

Any process left unfinished is deadlocked.

Detection frequency trades overhead for faster recovery.17 / 20

Recovery

Break the cycle at the lowest cost.

19

Terminate processes

Abort every deadlocked process, or stop them one at a time until the cycle disappears.

Tradeoff: lost work and potentially difficult cleanup.

Preempt resources

Take resources from selected processes, roll those processes back, and restart them later.

Tradeoff: rollback complexity and starvation risk.

Victim selection should minimize total recovery cost.19 / 20
