Deadlocks

When processes wait for resources that can never become available

Deadlock State

A set of processes becomes permanently blocked because each process is waiting for a resource held by another.

No process can move forward unless the cycle is broken.

A deadlock occurs when a group of processes becomes permanently blocked. Each process holds at least one resource while waiting for another resource held by a different process. In this example, P1 and P2 each hold one resource and request the other. Neither can continue because each waits for the other to release its resource.

Necessary Conditions for Deadlock

Mutual Exclusion

Only one process can use a particular resource at a time.

Hold and Wait

A process holds resources while requesting additional ones.

No Preemption

A resource must be released voluntarily by its holder.

Circular Wait

Each process waits for a resource held by the next process in a cycle.

Four conditions must exist at the same time for a deadlock to occur: mutual exclusion, hold and wait, no preemption, and circular wait. If the system eliminates any one of these conditions, it prevents deadlock.

Resource Allocation Graph

A Resource Allocation Graph, or RAG, shows which resources processes hold and which resources they request.

  • Circle: process
  • Rectangle: resource type
  • Process to resource: request edge
  • Resource to process: assignment edge

A cycle signals circular waiting.

With one instance of each resource type, a cycle confirms deadlock.

A resource allocation graph represents the relationship between processes and resources. In standard notation, circles represent processes and rectangles represent resource types. A request edge points from a process to a resource. An assignment edge points from a resource to a process. A cycle is an important warning sign.

Resource Allocation Graph

Follow the direction of the arrows. R1 is assigned to P1, which requests R2. R2 is assigned to P2, which requests R1. The chain returns to its starting point. Since each resource has one instance, this closed cycle represents a deadlock.

Deadlock Handling

Prevention

Stop any one of the necessary 4 conditions from occurring.

Avoidance

Grant a request only when the system remains in a safe state.

Detection and Recovery

Allow deadlock, detect it, then break the cycle.

Safe state: at least one completion sequence exists. An unsafe state creates risk, but does not automatically mean a deadlock already exists.

Operating systems handle deadlocks in three main ways. Prevention removes one necessary condition. Avoidance checks whether each allocation leaves the system safe. Detection and recovery allows deadlocks to occur, finds them, and then takes corrective action.

Deadlock Prevention Methods

Prevent the following:

Mutual Exclusion

Some resources, such as printers, cannot be shared. Eliminating this condition is often impractical.

Hold and Wait

Require a process to request every needed resource before it begins, or allow requests only when it holds none.

The tradeoff is lower resource utilization.

Some resources cannot be shared, so mutual exclusion is unavoidable. Hold and wait can be removed by requiring all resources up front or requiring a process to hold none when making a request. These approaches prevent deadlock but can leave resources reserved and unused.

Deadlock Prevention Methods

Prevent the following:

No Preemption

Take a resource from one process when another process needs it, provided the resource state can be saved and restored safely.

Circular Wait

Give resource types a fixed order and require every process to request them in increasing order.

A shared request order makes a circular chain impossible.

The no-preemption condition can be addressed by taking a resource away and later restoring the affected process. Circular wait can be prevented by numbering resource types and requiring every process to request them in the same increasing order.

Deadlock Avoidance: Banker’s Algorithm

Each process declares its maximum possible resource demand.

The system temporarily tests a new request.

If a safe completion sequence remains, the system grants the request.

If the state would become unsafe, the request waits.

Banker’s algorithm applies when resource types have multiple instances. Each process states its maximum demand. Before granting a request, the system simulates the allocation. It grants the request only when at least one safe sequence remains.

Safe State Example

Process Max Allocated Need
A B C A B C A B C
P1 2 1 1 1 0 0 1 1 1
P2 1 2 1 0 1 1 1 1 0
P3 3 1 2 1 1 0 2 0 2

Available A, B, C

[1, 1, 2]

P1 can finish because Need [1, 1, 1] is no greater than Available [1, 1, 2].

P1→P2→P3
This example has three resource types: A, B, and C. Need equals Max minus Allocation. We begin with Available equal to one, one, and two. P1 can finish first because its need does not exceed what is available. When P1 finishes, it releases its allocation, so Available becomes two, one, and two. P2 can then finish and release its resources, giving two, two, and three. Finally, P3 can finish. Because the sequence P1, P2, P3 allows every process to complete, the system is in a safe state.

Data Structures for Banker’s Algorithm

Structure Size Meaning
Available M Currently available instances of each resource type
Max N × M Maximum demand of every process
Allocation N × M Resources currently assigned to every process
Need N × M Resources each process may still require
Request N × M Pending requests from all processes
Need = Max − Allocation
Let N be the number of processes and M the number of resource types. Available records free resources. Max records each process’s maximum demand. Allocation records current assignments. Need equals Max minus Allocation. Request records pending resource requests. Together, these structures let the system test whether a safe sequence exists.

Deadlock Detection

Wait-for Graph Check

Follow the directed edges and check whether they return to the starting process.

A wait-for graph contains only process nodes. An arrow from one process to another means the first process waits for a resource held by the second. Here, P1 waits for P2, P2 waits for P3, and P3 waits for P1. The path returns to its starting point, so the graph contains a cycle and the system has detected a deadlock.

Recovery from Deadlock

P1→P2→P3→P1

Deadlock still exists

Choose a recovery method to break the circular wait.

Resources released: none

After detecting the cycle, the operating system must choose a victim. Terminating P3 releases all resources held by P3 and immediately breaks the cycle. Preemption temporarily removes a suitable resource from a selected process and reallocates it, although the victim may need to restart. Rollback returns a process to an earlier checkpoint, releases its later allocations, and allows the remaining processes to continue. Recovery breaks the deadlock, but it can lose work or delay a process.
